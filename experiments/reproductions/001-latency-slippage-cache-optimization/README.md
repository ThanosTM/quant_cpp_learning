## 1. 一句话结论

在不改变业务计算函数、不改变算法复杂度的前提下，逐步加入**批处理、软件预取、事件缓存行驱逐、双核解耦与 cache-line write-back**。两组独立的 3 次运行给出：

- A 组：p50 **1416 → 916 ns（-35.3%）**；
- B 组：p50 **1416 → 958 ns（-32.3%）**。

两组都稳定复现的是**前三步**：

- 批处理 + 预取：p50 到 1000 ns（约 -29%）；
- 事件行驱逐：p50 到 958 ns（约 -32%）；
- 第四步双核中，只有 **4c（解耦 + `dc cvac`）** 的均值稳定优于第三步约 4%~5%，p50 不劣于第三步；4a/4b 在两组数据里方向不一致。

原文是 510 → 329 ns（-35.5%），本机 A 组 p50 与它同量级；**稳定可复现的幅度约 -32%，单组最好 -35%**。原文的三个“微架构反例”在本机没有复现：`D=64` 没有出现 LFB 悬崖，反而最好；`NTA/stream` 提示没有出现 850 ns 的暴涨；`dc civac` 也没有看到 Fill Buffer 争抢。原因是 Apple M2 Pro 的未完成缺失队列/L2 MSHR 更深、缓存行是 128B、跨核缓存行迁移约 **96 ns**（原文脏行转移 27.7 ns），且 macOS 不开放 PMU 计数器与硬亲和性。**能复现的是宏观优化方向，不能照搬的是 Intel 的具体参数。**

## 2. 原文讲了什么

### 2.1 场景与内存足迹

每 5 微秒从网络环形缓冲区收到一条行情；标的现货价格变化后，需要遍历该标的关联的 64 个期权，重算价格，并在 alpha 信号越过阈值时触发交易。原文按 Intel 的 64B 缓存行拆账：

| 数据 | 缓存行数 |
|---|---:|
| 1 条行情事件 | 3 |
| 股票元数据 | 9 |
| 64 个期权对象（每个 2 行） | 128 |
| 单次事件合计 | 约 140 行 |

全局查找表加环形缓冲区约 50.7 MB，而 i9-14900KS 的 L3 只有 36 MB，工作集已经超出最后一级缓存。原文的四个回合：

| 回合 | 关键技术 | 回应的硬件猜测 | 原文 p50 |
|---|---|---|---:|
| 基准 | 串行逐个重算 | — | 510 ns |
| 第一步 | 批处理（D=4，释放 MLP） | 预测 | 469 ns |
| 第二步 | `_mm_prefetch(_MM_HINT_T0)` | 预测 | 414 ns |
| 第三步 | `clflushopt` 清理事件行 | 留存 | 409 ns |
| 第四步初版 | 双核 40 + 24 分工 | 所有权 | 364 ns |
| 第四步终版 | 解耦回读 + `_mm_clwb` | 所有权 | **329 ns** |

原文 p90 从 1012 ns 降到 555 ns（-45.2%）。失败案例同样重要：`D=64` 时硬件计数器记录到 1001 个周期挂在满载的 Fill Buffer 上；`_MM_HINT_NTA` 让延迟暴涨到 850 ns；用一条假 load 模拟预取则多付 292 个停顿周期。

### 2.2 复现的边界

微信文章以文字和结论为主，代码块/图片在抓取时不可见；原始 slides PDF 在本次网络环境下未能完整下载。因此本实验是**按原文描述重建的代表性实现，不是逐行移植**。重建时优先保留以下不变量：

- 事件 3 行、股票元数据 9 行、每个期权 2 行、每次事件 140 行的访问形态；
- 64 个期权相互独立，计算函数在四个版本中完全相同；
- 工作集明显超过本机最后一级缓存；
- 优化只改访存组织与指令，不改数学。

## 3. 实验环境与 x86 → ARM64 映射

### 3.1 本机平台

| 项 | 值 |
|---|---|
| CPU | Apple M2 Pro，12 核 = 8 P-core + 4 E-core |
| P-core L1D | 128 KB |
| P-core L2 | 16 MB / 4 个 P-core 一个 cluster；8 个 P-core 共 2 个 cluster |
| 末级缓存 | 无独立 L3，L2 即最后一级（每个 cluster 16 MB） |
| 缓存行 | 128 B（`hw.cachelinesize = 128`） |
| 内存 | 32 GB |
| OS | macOS 26.5.1（Build 25F80） |
| 编译器 | Apple clang 17.0.0 |
| 计时 | `mach_absolute_time`，24 MHz，41.67 ns/tick |

### 3.2 指令与语义映射

| 原文（Intel x86） | 本实验（Apple ARM64） | 说明 |
|---|---|---|
| `_mm_prefetch(_MM_HINT_T0)` | `prfm pldl1keep` | 预取到 L1 |
| `_MM_HINT_NTA` | `prfm pldl1strm` | 流式提示；ARM 语义不等价于 x86 NTA |
| `_mm_clflushopt` | `dc civac` | clean + invalidate to PoC |
| `_mm_clwb` | `dc cvac` | clean to PoC，保留本地副本 |
| 64B 缓存行 | 128B 缓存行 | 为保留“每对象 2 行”，对象填充到 256B |
| `rdpmc` / `perf` 计数器 | 不可用 | macOS 用户态不开放 PMU；`kperf` 需权限，本实验未用 |
| `sched_setaffinity` / 核绑定 | 不可用 | `thread_policy_set(THREAD_AFFINITY_POLICY)` 返回 `KERN_NOT_SUPPORTED (46)`；只能用 QoS 请求 P-core |

`dc civac/cvac` 在 macOS 的 EL0 可用，本机实测约 **1.44 ns/条**，并不是“系统调用级”开销。这很关键：第三步的收益/损失不是被指令成本吃掉的，而是被“驱逐后是否真的有用”决定的。

### 3.3 本机缓存与跨核探针

`./build/probe all` 的 3 次运行中位数：

| 工作集 / 操作 | 延迟 |
|---|---:|
| L1 64 KB 随机指针追逐 | 0.89 ns/load |
| L1 128 KB | 0.91 ns/load |
| L2 1 MB | 5.92 ns/load |
| L2 8 MB | 7.49 ns/load |
| L2 16 MB | 40.24 ns/load |
| DRAM 32 MB | 91.40 ns/load |
| DRAM 128 MB | 118.71 ns/load |
| 同一条热行的普通 load | 0.29 ns/op |
| `prfm pldl1keep` | 0.29 ns/op |
| `dc civac` | 1.44 ns/op |
| `dc cvac` | 1.43 ns/op |
| 128B 脏行跨核 handoff | 96.23 ns/handoff |
| 128B 脏行 + `dc cvac` | 116.32 ns/handoff |

16 MB 处从 7.5 ns 跳到 40 ns，正好对应一个 P-core cluster 的 16 MB L2 容量边界；32 MB 之后进入 DRAM 量级。跨核 handoff 的三次原始值为 82.6/96.2/122.1 ns，波动很大，原因见 §7：macOS 不保证两个线程落在同一 cluster 还是不同 cluster。

## 4. 案例模型

### 4.1 数据规模

| 项 | 值 |
|---|---|
| 标的（股票）数 | 16 384 |
| 每个标的的期权数 | 64 |
| 期权对象 | 256 B = 2 × 128B 行 |
| 股票元数据 | 1152 B = 9 × 128B 行 |
| 行情事件 | 384 B = 3 × 128B 行 |
| 事件数 | 240 000（前 40 000 条预热，不计入统计） |
| 期权池 | 16 384 × 64 × 256B ≈ 268 MB |
| 股票元数据 | 16 384 × 1152B ≈ 18.9 MB |
| 预填充环形缓冲区 | 240 000 × 384B ≈ 92 MB |
| 合计工作集 | 约 379 MB |

每次事件访问 3 + 9 + 128 = **140 条缓存行 / 17.9 KB**，与原文的行数完全一致；只是每行 128B，所以字节数翻倍。379 MB 远超 16 MB 的 cluster L2，绝大多数期权行来自 DRAM。

### 4.2 为什么把期权的块内顺序打乱

如果 64 个期权在同一 16 KB 块内顺序访问，硬件流预取器会把“顺序扫描”变成免费预取，掩盖 MLP/软件预取的差异。因此每个标的在初始化时生成一个 64 项的随机排列 `order[]`：

```cpp
Option& o = base[s.order[j]];   // base 是 16KB 连续块，但访问顺序随机
```

这样既保留了“一个标的 64 个期权、16 KB 局部块”的语义，又让地址流不可预测。代价是每只股票的 64 个期权不再按逻辑序号顺序存放，但对业务无影响（期权对象自带 `idx`）。

### 4.3 业务计算与校验

四个版本共用 [case.hpp](src/case.hpp) 中的 `evaluate_option()`：

- 读取期权静态行（strike、vol、maturity、multiplier、type）；
- 读取股票元数据的 9 行（spot、rate、div、8 行 vol surface）；
- 读取事件的后 2 行参数；
- 用同一个有界有理式 `signal(d)` 代替 Black-Scholes 的 CDF，固定每个期权的计算量，聚焦访存；
- 写回价格、delta、gamma、vega、`qprice = int64(price * 1e9)` 和 `hit`。

校验和只统计命中项：`hits`（命中数）、`qsum`（命中价格整数和）、`mix`（`qprice ^ idx` 的异或和）。这三个量对求和/异或顺序不敏感，因此双核版本把 40/48 个结果与辅核结果合并后，仍必须与单核版本逐位一致。

## 5. 四个优化步骤与实测

> 每个配置跑 3 次，取中位数；完整表见 [results/summary.md](results/summary.md)。计时器 41.67 ns/tick，**小于 1 tick 的差异不要当真**。

### 5.1 第一步：批处理（释放 MLP）

**问题**：原始循环逐个期权地“请求行 → 等待 → 计算 → 下一个”，虽然乱序引擎能自然重叠一部分缺失，但重叠度有限。

**做法**：把 64 个期权按 D 个一批拆成两趟。第一趟只摸每个期权的**对象首行**（对象地址，也就是一条缓存行），用普通 load 让多个缺失同时在途；第二趟再集中计算。第二趟计算时会读对象第二行，这一行仍可能缺失，但第一行的缺失已经被重叠掉了。

```cpp
for (int j = 0; j < 64; j += D) {
    for (int k = 0; k < D; ++k) {
        Option& o = base[s.order[j + k]];
        touch_line(&o);                 // 只摸首行，不读第二行
    }
    asm volatile("" ::: "memory");      // 防止计算被提前调度
    for (int k = 0; k < D; ++k) {
        Option& o = base[s.order[j + k]];
        evaluate_option(o, s, in);
        accumulate(total, o);
    }
}
```

**D 扫描（p50 / p90 / mean，ns）**：

| 配置 | p50 | p90 | mean | vs baseline p50 |
|---|---:|---:|---:|---:|
| 基线串行 | 1416 | 1666 | 1442.0 | — |
| D=4（原文参数） | 1375 | 1666 | 1412.7 | -2.9% |
| D=8 | 1291 | 1541 | 1341.1 | -8.8% |
| D=16 | 1166 | 1375 | 1225.2 | -17.7% |
| D=32 | 1041 | 1250 | 1110.9 | -26.5% |
| D=64 | 1041 | 1208 | 1077.8 | -26.5% |

**解读**：批处理本身是有效的（最多 -26.5%），但本机的最佳批次在 **D=64**，而不是原文的 D=4；`D=4` 甚至只比基线好 2.9%。这不是“原文错了”，而是 M2 的未完成缺失队列/L2 MSHR 比 i9 更深：第一趟只摸首行时 D=64 是 64 个在途请求，本机没有观察到 Fill Buffer 饱和。macOS 又不给 PMU 计数器，无法像原文那样读取“1001 个周期挂在 Fill Buffer 上”的证据，所以这里只能给出“没有悬崖”的实测，不能给出 stall cycle 数。

### 5.2 第二步：软件预取（把 load 换成便条）

**问题**：第一趟用的是普通 load，有目标寄存器、受 ROB 管辖；数据没回来之前指令不能退休，会逐渐堵住指令窗口。

**做法**：换成 `prfm pldl1keep`，没有目标寄存器，发射后即可退出。每个期权占 2 行，所以预取要发两条；采用“算当前批、预取下一批”的两批流水线：

```cpp
for (int p = 0; p <= distance; ++p) prefetch_batch(p);     // 前 distance+1 批
for (int j = 0; j < 64; j += D) {
    prefetch_batch(j + (distance + 1) * D);                // 提前一批
    compute_batch(j);
}
```

**结果**：

| 配置 | p50 | p90 | mean | 相对基线 p50 |
|---|---:|---:|---:|---:|
| 批处理 D=64（上一步最优） | 1041 | 1208 | 1077.8 | -26.5% |
| 预取 D=4，T0（原文参数） | 1083 | 1291 | 1128.0 | -23.5% |
| **预取 D=8，T0** | **1000** | **1166** | **1021.6** | **-29.4%** |
| 预取 D=8，stream | 1000 | 1166 | 1050.2 | -29.4% |

**解读**：

- 在本机参数下，预取 D=8 比“批处理最优”再快 3.9%（1041 → 1000）；如果拿 D=8 的批处理（1291）作参照，则是 -22.5%。
- `stream`（对应 `_MM_HINT_NTA`）的 p50 与 T0 相同，均值只差 2.7%；**没有出现原文 NTA 850 ns 的暴涨**。ARM 的 `pldl1strm` 只是流式提示，实际替换策略与 x86 NTA 不等价，M2 也不会因为“提前驱逐”而立即失去后续复用。
- 原文 T0 从 469 → 414 ns（-11.7%），本机从 1041 → 1000 ns（-3.9%）：预取的相对收益更小，因为 M2 的单核乱序/预取器已经能挖出较多 MLP，软件预取只是在 ROB 占用上再省一点。
- 独立 B 组 D=8 为 p50 1000 / p90 1208 / mean 1125.3；p50 与 A 组一致，说明预取这一步的 p50 收益稳定，均值受系统噪声影响。

### 5.3 第三步：驱逐事件行（留存）

**问题**：行情事件在当前 tick 算完后就是死数据，但默认伪 LRU 会把它留在 L1/L2，挤占长期复用的期权元数据。

**做法**：事件处理末尾对事件的 3 条缓存行执行 `dc civac`（x86 对应 `clflushopt`），并 `dsb ish`：

```cpp
process_event(...);
evict_line(&e);
evict_line((char*)&e + 128);
evict_line((char*)&e + 256);
publish_fence();
```

**结果**：

| 配置 | A 组 p50 / p90 / mean | B 组 p50 / p90 / mean | vs 上一步 p50 |
|---|---:|---:|---:|
| 预取 D=8 | 1000 / 1166 / 1021.6 | 1000 / 1208 / 1125.3 | — |
| + 驱逐事件行 | **958 / 1166 / 1012.9** | **958 / 1166 / 1029.7** | **-4.2% / -4.2%** |
| 原文对应：414 → 409 | 409 / — / — | — | -1.2% |

**解读**：两组 p50 都降了 42 ns（正好一个 41.67 ns 的 timer tick），方向一致；均值 A 组只降 0.9%，B 组降 8.5%，说明均值受线程/系统噪声影响更大。这一步可以算“p50 方向复现、幅度约一个 tick”，但**不能把均值改善当作稳定收益**。原文用硬件计数器看到“平均等待时间减少 21.3%”，本机没有 PMU，无法验证这个中间量。`dc civac` 本身只要 1.44 ns/条，3 条约 4.3 ns，不是瓶颈；真正的限制是事件行是**顺序流式读取**，硬件预取器本来就能把它的延迟藏掉，驱逐它并不会让期权行明显更常住。

补充：在 D=4 路径上，预取 1083 → 驱逐 1083（0 收益），说明这一步对参数/工作集很敏感，不能当成普适结论。

### 5.4 第四步：双核与所有权

**设计**：64 个期权互相独立，按 **48 + 16** 拆分（不是原文的 40 + 24）。原因：原文主核还要处理网络/事件分发，本实验的主核没有这部分额外工作；调参时 40+24 会让主核算完 40 个后明显空等辅核，48+16 更平衡。这个差异在 §7 明确标出。

同步与数据流：

1. 主核把事件参数（spot、threshold、7 个 double）打包到共享槽位 line 0，`seq.store(release)`；
2. 辅核轮询 `seq`，醒来计算 48..63；
3. 主核同时计算 0..47；
4. 辅核把结果写入共享区，`done.store(release)`；
5. 主核 `done.load(acquire)` 后读回结果。

三种回传方式：

- **4a 完整结果**：每个期权回传 2 行（价格、delta、gamma、vega、aux），16 个期权 = 32 行；主核全部读回。
- **4b 解耦命中列表**：辅核自己维护期权状态，只回传 `{qprice, idx}`（16B/条，通常 2~3 行）；主核不碰辅核的期权状态行。
- **4c 解耦 + `dc cvac`**：辅核在 `done.store` 前对命中列表所在行做 `dc cvac` + `dsb ish`，把脏数据推进共享 L2，同时保留本地副本（x86 `_mm_clwb` 的对应物）。

另外，针对 M2 加了一个原文没有的适配：主核在发信号前用 `prfm pldl2keep` 把辅核前两批期权拉到**共享 L2**，避免辅核“醒来才开始追冷缺失”。

**结果**：

| 配置 | A 组 p50 / mean | B 组 p50 / mean | vs 第三步（A / B） |
|---|---:|---:|---:|
| 第三步单核 | 958 / 1012.9 | 958 / 1029.7 | — |
| 4a 完整结果回传 | 958 / 1029.5 | 1083 / 1102.5 | 0% / +12.9%（更差） |
| 4b 解耦命中列表 | 916 / 996.1 | 1000 / 1201.4 | -4.4% / +4.4%（更差） |
| 4c 4b + `dc cvac` | 916 / 960.2 | 958 / 985.6 | -4.4% / 0% |

**解读**：

- 4a 的完整回传在 A 组 p90 从 1166 涨到 1250，在 B 组 p50/mean 都明显更差（1083/1102.5）：32 条脏行回传的代价可见。
- 4b 只在 A 组 p50 占优（916 vs 958）；B 组回落到 1000，均值 1201.4 反而最差。解耦本身有收益，但不稳定。
- **4c 是两组中唯一“均值稳定更优、p50 不劣”的双核版本**：相对第三步，A 组 mean -5.2%，B 组 mean -4.3%，p50 为 916/958（A 组 -4.4%，B 组持平）。这支撑了原文“解耦 + clwb”的方向，但幅度只有 4%~5%，远低于原文的 20%。
- 原文第四步初版 409 → 364（-11.0%），终版 → 329（-20.0%）；本机最好只有 -4.4%（p50）。差距的主因是**跨核 handoff 成本**：本机 128B 脏行 handoff 中位数 96 ns，原文脏行转移只有 27.7 ns；每事件至少两次握手（seq + done），约 200 ns 的同步成本吃掉了 16/64 的并行收益。macOS 又不能绑核，两个线程可能落在同一 cluster 或不同 cluster，导致 4a/4b/4c 的方差明显大于单核版本。
- `dc cvac` 单独探针的中位数是 116 ns/handoff，比不刷新的 96 ns 还慢；但 4c 在两组主基准里均值都优于 4b。解释：主基准里 `cvac` 减少的是主核读脏行的所有权转移，探针测的是另一条 handoff 路径，两者不能直接等同。
- 结论：**双核没有复现原文 20% 的收益；只有“解耦 + `dc cvac`”带来 4%~5% 的均值改善，p50 与单核第三步持平或略好。**

## 6. 结果汇总

### 6.1 累计优化（每个阶段取本机最优参数）

| 版本 | 关键改动 | A 组 p50 / p90 / mean | B 组 p50 / p90 / mean |
|---|---|---|---|
| 基线 | 串行逐个重算 | 1416 / 1666 / 1442.0 | 1416 / 1666 / 1433.5 |
| 第一步 | 批处理 D=64（B 组 D=32） | 1041 / 1208 / 1077.8 | 1166 / 1375 / 1199.9 |
| 第二步 | + 预取 D=8 T0 | 1000 / 1166 / 1021.6 | 1000 / 1208 / 1125.3 |
| 第三步 | + 驱逐事件行 | 958 / 1166 / 1012.9 | 958 / 1166 / 1029.7 |
| 第四步初版 | 双核 48+16，完整回传 | 958 / 1250 / 1029.5 | 1083 / 1250 / 1102.5 |
| 第四步终版 | 解耦回读 + `dc cvac` | 916 / 1125 / 960.2 | 958 / 1166 / 985.6 |
| 原文终版 | 双核 + clwb | 329 / 555 / — | — |

A 组 = [results/summary.md](results/summary.md)；B 组 = 独立复跑的 [results/repeat_summary.md](results/repeat_summary.md)。两组共同支持的结论是：**基线 → 预取** 都是 -29.4%，**基线 → 驱逐** 都是 -32.3%；第三步 p50 收益稳定。第四步只有 4c 的均值稳定改善 4%~5%，p50 不劣于第三步；4a/4b 方向不稳定。A 组的 916 ns 是两次 3-run 中最好的一组，稳定值应按 958 ns（-32.3%）引用。

### 6.2 原文同参数（D=4）路径

为了区分“参数差异”和“硬件差异”，单独跑一条接近原文参数的路径：

| 版本 | p50 (ns) | mean (ns) | vs 基线 |
|---|---:|---:|---:|
| 基线 | 1416 | 1442.0 | — |
| 批处理 D=4 | 1375 | 1412.7 | -2.9% |
| + 预取 D=4 T0 | 1083 | 1128.0 | -23.5% |
| + 驱逐 D=4 | 1083 | 1154.6 | -23.5% |

即使完全照抄原文的 D=4，本机也只能从 1416 降到 1083（-23.5%），比本机稳定的 -32.3%（最好 -35.3%）少 9~12 个百分点。**照搬 Intel 的最优参数会明显损失收益**，这是本实验最值得带走的工程结论之一：微架构参数必须在本机重扫，不能抄。

### 6.3 校验和

`./build/bench --stage verify` 在 7 个版本上全部一致：

```text

verify batch4       hits=6984306 qsum=1293815637696780558 mix=0xf0902a8b41bb871
```

完整输出见 [results/verify.txt](results/verify.txt)。这证明四个版本没有偷换数学、没有漏算期权；差异只来自访存组织。

## 7. 偏差、失败案例与局限

### 7.1 原文结论 vs 本机实测

| 原文结论 | 原文数据 | 本机数据 | 是否复现 | 原因 |
|---|---|---|---|---|
| 批处理 D=4 有效 | 510 → 469 ns | 1416 → 1375 ns（-2.9%） | 弱复现 | M2 乱序窗口/MLP 已经很强，D=4 的在途请求太少 |
| D=64 撞 LFB 悬崖 | 1001 cycles stall | D=64 反而最好（1041 ns） | **未复现** | M2 的 L1 未完成缺失队列/L2 MSHR 更深；且无法读 PMU 验证 stall |
| T0 预取 -11.7% | 469 → 414 ns | 1041 → 1000 ns（-3.9%） | 方向复现，幅度小 | 单核已有较高 MLP，预取主要省 ROB 占用 |
| NTA 暴涨 | 414 → 850 ns | 1000 → 1000 ns（p50 不变，均值 +2.7%） | **未复现** | ARM `pldl1strm` 与 x86 NTA 语义不等价 |
| 假 load 预取 +292 stall | 多 292 cycles | 未实现该变体 | 未测 | 本实验第一步用的是真 load，没有单独做“假 load”对照 |
| clflushopt 清理事件行 -1.2% | 414 → 409 ns | A：1000 → 958（-4.2%）；B：1000 → 958（-4.2%） | 方向复现，均值不稳定 | 事件行顺序流式读取，硬件预取已藏掉大部分延迟；无 PMU 验证等待时间 |
| 双核初版 -11% | 409 → 364 ns | A：958 → 958（0%）；B：958 → 1083（+12.9%） | **未复现** | 跨核 handoff 96 ns vs 27.7 ns；完整回传 32 行脏数据 |
| 双核终版 -20% | 409 → 329 ns | A：958 → 916（p50 -4.4%）；B：958 → 958（p50 0%，mean -4.3%） | 弱复现（仅均值） | 同上；48+16 分核、macOS 不绑核，方差大 |
| 总 p50 -35.5% | 510 → 329 ns | A：1416 → 916（-35.3%）；B：1416 → 958（-32.3%） | 部分复现（稳定 -32%，最好 -35%） | 主要收益来自第一步 MLP + 第二步预取，第三/四步贡献较小 |
| 总 p90 -45.2% | 1012 → 555 ns | A：1666 → 1125（-32.5%）；B：1666 → 1166（-30.0%） | 未完全复现 | 无实时调度/绑核，尾延迟受系统噪声影响；单事件计时 41.67 ns 量化 |

### 7.2 为什么稳定收益仍有约 -30%

- 基线每次事件要碰 140 行，工作集 379 MB，绝大多数来自 DRAM；基线 p50 1416 ns，说明“等内存”是主矛盾。
- 第一步把 64 个期权首行的缺失尽量并行，直接拿掉约 18%~26%（取决于 D）；
- 第二步把普通 load 换成无目标寄存器的预取，把总收益推到约 29%；
- 第三步驱逐事件行再拿掉约 4%，两组 p50 都到 958 ns（-32%）；
- 第四步只有 4c 的均值再改善约 4%~5%，p50 不再明显下降。
- 这与原文“数学没变、只是和缓存逻辑博弈”的叙事一致；稳定复现的是前三步。

### 7.3 局限（必须写进任何引用本实验的结论里）

1. **没有 PMU**：不能读 LFB stall、L1/L2 命中率、等待时间；只能测端到端延迟，并用 D 扫描/探针间接推断。
2. **计时量化 41.67 ns**：p50 的一个 tick 差异（如 1000 → 958）不能单独当成强证据；本实验用两组独立 3 次运行中位数来暴露不稳定性，而不是只挑最好的一组。
3. **没有硬亲和性**：`thread_policy_set(THREAD_AFFINITY_POLICY)` 返回 46（不支持），双核结果随线程落点波动；4a/4b/4c 的 p99 尤其不稳。
4. **合成负载**：事件是预生成后整段刷出缓存的，模拟 DMA 写入的环形缓冲区；真实网卡/内核旁路路径还会引入 PCIe、DMA、NUMA/内存控制器等差异。
5. **计算函数是替身**：用有界有理式代替 Black-Scholes，目的是固定计算量、突出访存；它不能用于真实期权定价。
6. **单机、单进程**：没有其他负载隔离、没有实时调度、没有关闭后台任务；数据只代表这台 M2 Pro 在本次会话中的表现。
7. **重复性有限**：B 组独立复跑后，第三步 p50 仍为 -4.2%（稳定），但第四步 4b 从 -4.4% 反弹到 +4.4%，4a 也变差；只有 4c 的均值改善在两组中一致。引用本文时请用“约 -32%”，不要用 A 组最好的 -35.3%。

## 8. 复现方式与文件说明

### 8.1 命令

```bash
cd experiments/reproductions/001-latency-slippage-cache-optimization
make -j4 all                 # 编译 bench 与 probe
./run_all.sh                 # 14 个配置 × 3 次 + 汇总 + verify + 探针
./run_repeat.sh              # 独立复跑关键配置，生成 repeat_*
./build/bench --stage verify # 只跑校验和
./build/probe all            # 缓存层次 / 指令成本 / 跨核迁移
```

`run_all.sh` 会生成：

- `results/raw.csv`：每个配置 3 行的原始数据；
- `results/summary.md`：按配置分组的中位数表；
- `results/verify.txt`：7 个版本的校验和一致性；
- `results/probe_1..3.txt`：环境探针原始输出。

另有一组独立复跑（A 组生成后再手动跑一遍关键配置），用于检验结论稳定性：

- `results/repeat_raw.csv`：基线 + 批处理 + 预取 + 驱逐 + 4a/4b/4c 的第二组 3 次数据；
- `results/repeat_summary.md`：第二组中位数。两组对比见 §6.1。

### 8.2 单跑

```bash
./build/bench --stage 0                                   # 基线
./build/bench --stage 1 --batch 64                        # 批处理
./build/bench --stage 2 --batch 8 --hint t0               # 预取
./build/bench --stage 2 --batch 8 --hint stream           # NTA 对应物
./build/bench --stage 3 --batch 8 --hint t0               # 驱逐
./build/bench --stage 4a --split 48                       # 双核完整回传
./build/bench --stage 4b --split 48                       # 双核解耦
./build/bench --stage 4c --split 48                       # 解耦 + cvac
```

### 8.4 复跑注意

- 接电源、关闭高负载后台程序；macOS 的调度/频率策略会直接影响 p99。
- 每个配置至少 3 次；比较时看 3 次中位数，不要拿单次 p50 的 1 tick 差异下结论。
- 若换机器，先跑 `./build/probe all` 重新建立缓存层次基线，再重扫 D；**不要直接套用本文的 D=64/D=8**。

## 9. 待验证问题

1. **能否拿到 PMU**：`kperf` 在 macOS 上需要权限/entitlement；若能启用，可直接验证 LFB stall、L1/L2 命中率、跨核 snoop 次数，把“间接推断”变成“直接证据”。
2. **双核落点**：能否用 `os_workgroup`、thread QoS + cluster 提示或私有 API 控制两个 P-core 落在同一/不同 L2 cluster？当前只能靠多次运行取中位数。
3. **x86 对照**：本实验没有第二台 Intel 机器；若在 Linux x86 上跑同一份代码（`_mm_clflushopt/_mm_clwb` 分支已写好），可以直接验证 D=64 悬崖与 NTA 反例。
4. **假 load 变体**：原文用假 load 模拟预取多付 292 个停顿周期；本实验未实现该分支，后续可加 `stage2_fake_load` 做直接对照。
5. **事件流水**：把单事件握手改成双缓冲的两事件流水，是否能摊薄 2×96 ns 的跨核 handoff，让双核收益更接近原文？这是下一步最值得做的实验。
