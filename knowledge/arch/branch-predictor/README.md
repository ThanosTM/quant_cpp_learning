# 分支预测与预测失败惩罚

> 模块: arch ｜ 状态: expanded ｜ 深度: L2 ｜ 创建: 2026-11-04 ｜ 更新: 2026-11-04
> 依据: JD 点名「分支预测」；arch 主线第 2 站（P0）；与 [low-latency/branch-and-inline](../../low-latency/README.md)（规划中）交叉。

## 1. 一句话定位

CPU 在前端取指时不知道条件分支走哪边，只能**预测**；预测对了流水线不断流，预测错了要清空前端并从正确目标重新取指——这就是「有序数组比无序数组快 7 倍」的根源。

## 2. 为什么面试官爱问

- 现象极其经典：同一段条件求和代码，数据排好序就快一个数量级；面试官用它区分「知道 branch predictor 这个词」和「知道它预测什么、失败花多少代价、怎么写 branchless」。
- 与低延迟岗位直接相关：订单簿、风控、撮合热路径里到处都是数据相关的条件分支；把不可预测分支改成无分支写法，是常见的微秒级优化。
- 与流水线、乱序执行直接相连：预测失败惩罚本质上取决于前端深度与恢复机制，下一站 [pipeline-superscalar](../pipeline-superscalar/README.md) 会展开。
- 与 [low-latency/branch-and-inline](../../low-latency/README.md)（规划中，`[[likely]]`/内联权衡）是同一主题的工程侧。

## 4. 核心讲解

### 4.1 分支在前端做了什么

现代 CPU 的前端大致是：

```text
取指 → 预测方向/目标 → 继续取指 → 解码 → 发射 → 执行
                 |
                 +-- 预测错 → 清空前端流水线，从正确目标重新取指
```

两个预测对象：

- **方向（direction）**：这个条件分支跳不跳？
- **目标（target）**：如果跳，跳到哪里？由 BTB（Branch Target Buffer）缓存「分支指令地址 → 目标地址」。

预测正确时，前端可以继续按预测路径取指，分支几乎"免费"；预测错误时，已经进入前端的错误路径指令要被丢弃（flush），并从正确目标重新填充。代价通常是十几到几十个周期，具体取决于流水线深度、前端宽度和恢复机制。

### 4.2 预测器怎么工作

- **静态预测**：编译期规则（如「向后跳转预测 taken、向前预测 not taken」）或 profile-guided 信息；简单但不适应运行时数据。
- **1-bit 预测器**：每个分支记一个「上次跳没跳」；遇到一次例外就连续错两次（第一次改状态，第二次才预测对）。
- **2-bit 饱和计数器**：强不跳 / 弱不跳 / 弱跳 / 强跳；需要连续两次相反结果才翻转，能过滤偶发抖动，是最经典的入门模型。
- **相关/历史预测器**：用全局分支历史（例如最近 N 个分支的结果）做索引，能识别 `if (x) ... else ...` 之间的相关性；现代高性能核常用 **TAGE**（多历史长度、带标签的几何历史预测器）。
- **循环预测器**：识别固定次数循环的退出分支；**返回栈**（RAS）预测函数返回地址；**间接分支预测**处理虚函数/函数指针。
- Apple 未公开具体预测器微架构；面试答「两级/相关/TAGE 类 + BTB + RAS」是合理框架，不要编造具体表大小。

### 4.3 预测失败惩罚

一次 mispredict 的成本不是固定常数，而是：

```
错误路径已经取指/解码的指令数 × 前端吞吐 + 重新取指延迟 + 流水线恢复开销
```

本机实测（见 §5）：随机数据下每次元素的条件分支约 **3.06 ns**，有序数据约 **0.40 ns**；按 50% 误预测粗估，单次误预测约 **5.3 ns**（约 18 个 3.5 GHz 周期，含其它执行差异）。这个数字随微架构、频率、分支密度变化，只能当量级参考。

### 4.4 无分支写法：CSEL / CMOV

编译器可以把简单的 `if` 转成**条件选择指令**（ARM64 `CSEL`、x86 `CMOV`），代价是两边都算、再选一个：

```cpp
// 分支版：可能被编译器 if-convert；用屏障强制保留分支
if (data[i] >= threshold) {
    sum += data[i];
    asm volatile("" ::: "memory");
}

// 无分支版：条件选择，不依赖方向预测
sum += (data[i] >= threshold) ? data[i] : 0;
```

什么时候无分支更好：

- 条件结果**不可预测**（随机 50/50）→ 消除误预测，通常大赚；
- 条件结果**高度可预测**（排序、循环边界）→ 分支可能比无分支更快，因为无分支要额外执行选择/计算；
- 两边计算都很贵时 → 无分支会做双倍工作，可能更慢；
- 有副作用（store、函数调用、异常）时 → 编译器通常不能 if-convert，必须保留分支。

`[[likely]]` / `[[unlikely]]` / `__builtin_expect` 是**给编译器的静态布局提示**，不是给硬件预测器的运行时信息；在 ARM64 上通常只影响代码布局/内联，不会让随机分支变可预测。错误路径用 `[[unlikely]]` 有意义（减少 I-cache 占用、改善布局），但别指望它替代 branchless。

### 4.5 怎么写出/测出差异

- **控制变量**：有序/无序数组必须是同一组数据、同样的访存模式，只改顺序；本实验用同一份随机数据排序前后对比。
- **禁用向量化**：否则无分支版本可能被 SIMD 化，测到的是 SIMD 而不是分支；用 `#pragma clang loop vectorize(disable)`。
- **防止 if-conversion**：在 `if` 内放 `asm volatile("" ::: "memory")`，编译器不能把有副作用的代码提到分支外；再用汇编确认（本实验 `sum_branch` 生成 `tbz` 分支，`sum_branchless` 生成 `and/asr` + `add`，没有分支）。
- **warmup + 多次取中位数**：第一次跑有 page fault、频率爬升、预测器冷启动；至少 5 次取中位数。
- **不要只看平均**：真实系统里分支误预测会造成尾延迟尖刺；微基准看吞吐，生产看 p99/p999。

### 4.6 量化交易场景映射

- **订单簿/撮合**：价格比较、数量判断、状态机分支高度依赖数据；如果分支不可预测，考虑 branchless 选择或查表。
- **风控/限额检查**：绝大多数时候通过、极少拒绝——这类分支高度可预测，保留 `if` 更好，错误路径用 `[[unlikely]]`。
- **行情解析**：消息类型 switch/跳转表；间接分支预测失败也会造成前端停顿。
- **热路径原则**：先用 `perf stat -e branch-misses` / Instruments 确认误预测率，再决定是否 branchless；不要盲目把所有 `if` 改成三元表达式。

### 4.7 常见误区

- 「branchless 一定更快」：错。可预测分支几乎免费，branchless 反而多做事。
- 「`[[likely]]` 能让 CPU 预测得更准」：错。它主要是编译期布局提示，硬件仍按运行时历史预测。
- 「编译器一定会把 if 变成 CSEL」：不一定；有副作用、函数调用、复杂条件时仍保留分支，必须看汇编。
- 「分支预测器能学会任意模式」：简单交替模式可能被历史预测器学到，但 50/50 随机数据没有规律，误预测率接近 50%。
- 「误预测惩罚是一个固定周期数」：随流水线深度、频率、前端状态变化；只能实测量级。

## 5. Example 说明

```bash
g++ -std=c++20 -O2 -Wall example.cpp -o example && ./example
```

本机环境：Apple M2 Pro / macOS 26.5.1（Darwin 25.5.0）/ arm64 / Apple clang 17；N=32,000,000 个 `uint8_t`，threshold=128，每个配置 5 次取中位数，整体跑 3 次再取中位数。

**实验一：有序 vs 无序**

| 版本 | 时间 | ns/元素 |
|---|---|---|
| sorted branch | 12.97 ms | 0.405 |
| random branch | 97.85 ms | 3.058 |

- 随机/有序 = **7.55x**。
- 按「随机数据约 50% 满足条件、每次误预测都付出代价」粗估：单次误预测约 **5.3 ns**（含其它执行差异，不是精确周期数）。

**实验二：随机数据的分支 vs 无分支**

| 版本 | 时间 | ns/元素 |
|---|---|---|
| random branch | 97.85 ms | 3.058 |
| random branchless | 16.07 ms | 0.502 |

- 分支/无分支 = **6.11x**。
- 注意：branchless 仍然比 sorted branch（0.405 ns）慢——它总是执行比较/选择，只是没有误预测。

**实验三：分支模式敏感性**

| 模式 | 时间 | ns/元素 |
|---|---|---|
| sorted（先全不满足，后全满足） | 12.97 ms | 0.405 |
| alternating（0,255,0,255…） | 19.10 ms | 0.597 |
| random（50/50 无规律） | 97.85 ms | 3.058 |

- 交替/随机 = **0.20x**（即交替比随机快约 5x）：现代历史预测器能学到简单的交替模式，但不如全有序干净。

**汇编核对**

- `sum_branch`：`tbz w10, #31`（检查符号位）→ 真分支。
- `sum_branchless`：`and w10, w10, w10, asr #31` + `add` → 无分支的条件选择。

这证明实验对比的是「分支 vs 无分支」，而不是编译器把两者都优化成同一种形态。

## 6. 高频面试问答

| 问题 | 30 秒速答 |
|---|---|
| 分支预测器预测什么？ | 方向（跳不跳）+ 目标（跳去哪）；目标由 BTB 缓存，返回地址由 RAS 预测 |
| 为什么有序数组比无序快？ | 有序数据的分支结果成段重复，预测器能学会；随机 50/50 无法预测，误预测率接近 50% |
| 2-bit 预测器怎么工作？ | 强/弱 taken、强/弱 not taken 四态；连续两次相反结果才翻转，过滤偶发噪声 |
| 预测失败惩罚多少？ | 前端 flush + 重新取指，通常十几到几十周期；本机粗估约 5.3 ns，只能当量级 |
| branchless 一定更快吗？ | 不一定；可预测分支几乎免费，branchless 会多执行选择/计算，可能更慢 |
| `[[likely]]` 能让分支变快吗？ | 它主要是编译期布局提示，不改变硬件的运行时预测；错误路径用 `[[unlikely]]` 有意义 |
| 编译器什么时候把 if 变成 CSEL/CMOV？ | 简单、无副作用、两边可安全提前计算时；有 store/函数调用/异常时通常保留分支 |
| 怎么确认代码里有没有分支？ | 看汇编：ARM64 `b.cond`/`tbz` vs `csel`；x86 `jcc` vs `cmov` |
| 怎么定位真实程序的分支问题？ | Linux `perf stat -e branch-misses` / `perf record`；macOS Instruments；先测量再改 |
| 间接分支（虚函数/函数指针）怎么预测？ | BTB + 间接分支预测器；多目标时容易误预测，热路径避免频繁变化的虚调用 |
