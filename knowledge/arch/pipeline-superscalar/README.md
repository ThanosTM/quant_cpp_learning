# 流水线、乱序执行与 IPC

> 模块: arch ｜ 状态: expanded ｜ 深度: L2 ｜ 创建: 2026-11-04 ｜ 更新: 2026-11-04
> 依据: 面试高频「CPU 是怎么跑快的」；arch 主线第 3 站（P1）；承接 [branch-predictor](../branch-predictor/README.md)，为 [simd](../simd/README.md)（规划中）铺路。

## 1. 一句话定位

流水线把一条指令拆成多级、让多条指令重叠执行，提高**吞吐**而不是单条延迟；超标量与乱序执行在一个周期发射多条指令，用寄存器重命名和 ROB 挖掘**指令级并行（ILP）**。程序性能 ≈ `IPC × 频率`，而 IPC 的上限由依赖链、执行单元数量和前端/后端资源共同决定。

## 2. 为什么面试官爱问

- 这类题是「CPU 怎么跑快」的标准追问链：流水线 → 冒险 → 超标量 → 乱序 → 寄存器重命名 → ROB → IPC。
- 有可直接观察的现象：同样求和，1 个累加器 vs 8 个累加器差 6 倍；纯 ALU 依赖链 vs 8 条独立链差 8 倍——能把「依赖链限制 ILP」讲清楚就是区分度。
- 与低延迟岗位直接相关：热路径里的循环依赖、累加、状态更新，往往不是「指令多」而是「依赖长」；多累加器、拆分归约是常见优化。
- 与 [branch-predictor](../branch-predictor/README.md)（控制冒险）、[cache-hierarchy-mesi](../cache-hierarchy-mesi/README.md)（访存停顿）、[simd](../simd/README.md)（数据级并行）构成完整的性能解释链。

## 4. 核心讲解

### 4.1 流水线：延迟不变，吞吐提高

经典五级流水线：

```text
IF → ID → EX → MEM → WB
```

- **延迟（latency）**：一条指令从进入到完成的时间，流水线不会让它变短，甚至因寄存器/旁路变长。
- **吞吐（throughput）**：理想情况下每个周期完成一条指令；级数越深，理论上吞吐越高，但冒险和恢复代价也越大。

三类冒险：

| 冒险 | 原因 | 常见处理 |
|---|---|---|
| 结构冒险 | 两条指令争同一硬件资源 | 增加端口/分离 I-cache 与 D-cache |
| 数据冒险 | 后一条指令依赖前一条的结果（RAW） | 转发（forwarding）、停顿、编译器调度 |
| 控制冒险 | 分支结果未知，取指方向不确定 | 分支预测 + 预测失败 flush（见第 2 站） |

转发能让 `add` 的结果直接送给下一条指令，减少停顿；但有些延迟（如 load-use、长延迟 FP 运算）仍需要 stall。

### 4.2 超标量、乱序与寄存器重命名

- **超标量（superscalar）**：一个周期取指/解码/发射多条指令，前提是有足够的执行单元和寄存器端口。
- **乱序执行（out-of-order）**：指令按程序顺序进入，但在操作数就绪后可以乱序执行；结果按程序顺序提交（in-order retire）。
- **寄存器重命名**：把架构寄存器映射到物理寄存器，消除 WAR/WAW 这类「假依赖」，只保留真正的 RAW 依赖。
- **ROB（Reorder Buffer）**：记录在途指令，保证精确异常与按序提交；ROB 满或调度器满时，前端会被反压。
- **存储缓冲/内存消歧**：load 可以绕过尚未提交的 store，但必须做地址消歧，避免读错数据。

关键结论：**乱序执行能挖掘窗口内的 ILP，但不能打破真正的数据依赖**。一条 `s += x` 的循环依赖链，即使 CPU 再宽，也只能按加法延迟一步步走。

### 4.3 依赖链 vs ILP：为什么多开累加器有效

浮点归约 `sum += data[i]` 是一条**循环携带依赖**（loop-carried dependency）：第 i 次加法必须等第 i-1 次加法完成。若 FP add 延迟是 L 个周期，单累加器的吞吐上限是 `1/L` 次/周期。

拆成 2/4/8 个累加器后，每条链仍然有 L 周期延迟，但多条链可以交错执行，吞吐上限变成 `min(执行单元吞吐, 链数/L)`。这就是 ILP：

```text
单链:   s0 += x0 → s0 += x1 → s0 += x2 → ...   （串行，等延迟）
四链:   s0 += x0   s1 += x1   s2 += x2   s3 += x3
        s0 += x4   s1 += x5   s2 += x6   s3 += x7   （四条链并行）
```

本机实测（见 §5）：

- 1 → 2 → 4 → 8 个累加器：0.910 → 0.462 → 0.246 → 0.142 ns/元素，约 1.0x → 2.0x → 3.7x → 6.4x。
- 纯 ALU 链：1 条链 0.912 ns/add，8 条独立链 0.113 ns/add，约 **8.0x**。

为什么 8 累加器不是 8.0x：

- FP add 的执行单元吞吐有限，8 条链也会撞到端口/发射宽度上限；
- 归约还要加载数据，load、循环控制、地址计算都占资源；
- 调度器窗口、ROB、寄存器端口都会限制同时执行的指令数；
- 纯 ALU 链没有访存，所以更接近理论上限（8.0x）。

### 4.4 编译器能做什么、不能做什么

- 编译器可以**展开循环、重排独立指令、分配寄存器**，但**不能在没有 `-ffast-math` 的情况下重排浮点加法**——因为浮点加法不满足结合律，重排会改变舍入结果。
- 因此 `sum += data[i]` 的依赖链是语言语义层面的，编译器不会自动帮你拆成 8 个累加器；需要手动拆分归约。
- 整数加法满足结合律，编译器在某些情况下可以更自由地重排；但仍有溢出/有符号语义约束。
- `-ffast-math` 会放开重排/向量化，但会破坏 NaN/Inf/舍入语义；量化计算要明确是否可接受。
- 编译器可能做 SLP（superword-level parallelism）向量化，把多个标量加法合成 SIMD；这会混淆「ILP」和「SIMD」的测量，本站用内联汇编屏障强制标量（见 §5）。

### 4.5 IPC、CPI 与性能模型

```
IPC = instructions / cycles
CPI = cycles / instruction = 1 / IPC
执行时间 ≈ 指令数 × CPI / 频率
```

- IPC 不是固定值：依赖链、cache miss、分支误预测、前端宽度、执行单元数量都会压低它。
- 提高 IPC 的手段：拆分依赖链、提高 ILP、减少分支/ miss、向量化（SIMD 提高每指令工作量，不完全等于 IPC）。
- 提高频率的手段：更深流水线、更好的工艺/电压；但深流水线会加大误预测惩罚和功耗。
- 真实测量：Linux `perf stat -e cycles,instructions` 直接给 IPC；macOS 没有 Linux `perf`，用 Instruments（CPU Counters）或自建计时估算。

### 4.6 量化交易场景映射

- **PnL/统计归约**：不要用单累加器串行求和；拆 4/8 个累加器，最后合并。
- **订单簿更新**：状态机/链表遍历常有跨迭代依赖；先识别依赖链，再考虑拆分或改变数据结构。
- **热路径循环**：长依赖链会造成固定延迟下限，单纯增加核数/线程不能解决单线程延迟。
- **吞吐 vs 延迟**：撮合/风控关心单笔延迟，回测/统计关心吞吐；优化目标不同，ILP 手段的优先级也不同。
- **SIMD 之前先做 ILP**：标量多累加器往往是最低成本的一步；下一步才是向量化（第 4 站）。

### 4.7 常见误区

- 「流水线越深越快」：吞吐可能提高，但分支误预测/冒险恢复代价更大，延迟也更高。
- 「乱序执行能消除所有依赖」：只能消除假依赖（WAR/WAW），真正的 RAW 依赖仍在。
- 「多开累加器一定 8x」：受执行单元吞吐、load、循环开销、调度窗口限制；本机 8 累加器约 6.4x。
- 「编译器会自动帮我拆归约」：没有 `-ffast-math` 时不会重排 FP 加法。
- 「IPC 越高频率越低就更好」：执行时间取决于 IPC × 频率的乘积，且受功耗/散热约束。
- 「微基准的 ns/元素等于生产延迟」：生产还有 cache miss、分支、调度、内存带宽竞争。

## 5. Example 说明

```bash
g++ -std=c++20 -O2 -Wall example.cpp -o example && ./example
```

本机环境：Apple M2 Pro / macOS 26.5.1（Darwin 25.5.0）/ arm64 / Apple clang 17；每个配置 5 次取中位数，整体跑 3 次再取中位数。

**实验一：浮点归约，累加器数量**

| 版本 | 时间 | ns/元素 | 相对 1 累加器 |
|---|---|---|---|
| sum1 | 7.28 ms | 0.910 | 1.00x |
| sum2 | 3.70 ms | 0.462 | 1.97x |
| sum4 | 1.97 ms | 0.246 | 3.70x |
| sum8 | 1.14 ms | 0.142 | 6.39x |

N=8,000,000 个 `double`（约 61 MB）。数据全部为 1.0，避免随机值带来的额外差异。

**实验二：纯 ALU 依赖链**

| 版本 | 时间 | ns/add | 相对 1 条链 |
|---|---|---|---|
| chain1（1 条依赖链） | 91.21 ms | 0.912 | 1.00x |
| chain8（8 条独立链） | 11.35 ms | 0.113 | 8.01x |

N=100,000,000 次加法；`KEEP_FP` 内联屏障防止编译器把 `x += 1.0` 折叠成闭式表达式。

**汇编核对**

- `sum1`：每轮 1 条 `fadd d0, d0, d1`，一条长依赖链。
- `sum4` / `sum8`：每轮 4/8 条标量 `fadd d`，**没有** `fadd.2d`——强制关闭了 SLP 向量化，测的是标量 ILP，不是 SIMD。
- `chain1`：每轮 1 条 `fadd`；`chain8`：每轮 8 条独立 `fadd`。

**估算**

- 若 P-core 约 3.5 GHz，`chain1` 的 0.912 ns/add ≈ 3.2 个周期/加法，说明 FP add 延迟约 3 个周期；`chain8` 的 0.113 ns/add ≈ 0.4 个周期/加法，约 2.5 条加法/周期——从「延迟 bound」转为「吞吐 bound」。
- `sum8` 的 6.4x 低于 `chain8` 的 8.0x，差额来自数据加载、地址计算和循环开销；纯 ALU 实验更接近理论上限。

## 6. 高频面试问答

| 问题 | 30 秒速答 |
|---|---|
| 流水线为什么能提高性能？ | 多条指令重叠执行，提高吞吐；单条指令延迟不会变短，甚至因级数变长 |
| 三类冒险是什么？ | 结构（资源冲突）、数据（RAW/WAR/WAW）、控制（分支方向未知）；转发/停顿/预测处理 |
| 超标量和乱序执行的区别？ | 超标量是「一个周期发射多条」，乱序是「按操作数就绪执行、按序提交」；两者常一起出现 |
| 寄存器重命名解决什么？ | 消除 WAR/WAW 假依赖，把架构寄存器映射到更多物理寄存器 |
| ROB 的作用？ | 记录在途指令，保证按序提交和精确异常；满了会反压前端 |
| IPC 和 CPI 是什么关系？ | IPC = 指令数/周期，CPI = 周期/指令，互为倒数；执行时间 ≈ 指令数 × CPI / 频率 |
| 为什么多累加器能提速？ | 打破循环携带依赖，让多条独立链并行；上限由执行单元吞吐和资源决定 |
| 为什么 8 累加器不是 8x？ | FP add 端口/发射宽度有限，load、循环、调度窗口都占资源；纯 ALU 链才能接近 8x |
| 编译器会自动拆归约吗？ | 没有 `-ffast-math` 不会；FP 加法不满足结合律，重排会改变舍入 |
| 怎么测 IPC？ | Linux `perf stat -e cycles,instructions`；macOS 用 Instruments CPU Counters 或自建计时估算 |
| 深流水线的代价？ | 分支误预测惩罚更大、功耗/面积更高、恢复更复杂；不是越深越好 |
